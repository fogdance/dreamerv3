## F0：多合约教材读取（`thinking_student/corpus.py`）
- **`TSCorpus`**
  - market 用 `C.load_arrays(..., mmap='r')` 映射读取，只检查行数（不对映射数组做全量 finite 扫描）。
  - facts、strict、behaviors 较小，照旧整读。
  - `window(name, lo, hi, market=True)`：`market=False` 时只返回账户和标签。
- **`CorpusWindows`**
  - 允许 `holdout=0`，此时 train/all 使用全部行；`split='eval'` 配 holdout 0 时报错。
  - 示范计数、`summary()`、`outcome_allowed()` 改用 `market=False`。
  - 从 `sample` 中拆出 `_pick(n, length)`，供多合约层复用。
- **新函数 `discover(root, contracts='discover'|list)`**
  - 只收有 `source.json` 且 `fold == TRAIN` 的目录。
  - 检查必需子目录存在。
  - 所有合约的 reward_schema、clock、gamma 必须一致，不一致时点名该合约并拒绝。
  - 合约名重复时拒绝。
  - 合约名单以磁盘为准，源码不写死。
- **新类 `MultiCorpusWindows(parts, mix='uniform_contract'|'proportional_rows', contract_weights=None, seed)`**
  - 每合约一个 `CorpusWindows`，共用一个 rng。
  - `sample`：每个 batch 行先按 mix 抽合约，再在该合约内抽窗口。窗口只由该合约的 `TSCorpus.window` 生成，**不跨合约**。
  - 记录各合约曝光次数，`last` 列出 (合约, 账户, 起点)，供测试核对。
  - L3 类别权重：weight='demo' 时，对所选合约 P0 示范的合并计数算一次 `L.class_weights`，所有合约统一使用（C4 §2.2-4）。
  - `batches`：按合约依次给出完整 batch，用于内部诊断评估。
  - `summary`：给出各合约和合计的真实样本、标签数。
- **采样器状态不另存文件。** 每条训练命令开始时，种子取 `SeedSequence([seed, stage, 该阶段已完成更新数])`。续训得到确定的新序列，最多重做最后一段未提交的 batch，符合 C4 §4.3-3。

## F1：多合约 L1→L2→L3、分段保存、π0（`thinking_student/run.py`）
- **CLI 新参数**
  - `--corpus` 改为可重复，`--cf` 同样可重复。
  - `--mix`、`--save-every`。
  - `--holdout 0` 表示全 TRAIN；holdout > 0 时，报告标 `TRAIN_INTERNAL_DIAGNOSTIC`。
  - `collect` / `check` / `cf` / `rollout` 只接受一个 corpus。
- **训练命令统一用 `MultiCorpusWindows`**
  - L1 用全部账户，L2/L3 用 `LABEL_ACCOUNT` P0。
  - 每 `save_every` 次更新调用一次 `save()`。
  - holdout 0 时不做 eval，报告的 `eval` 为空。
- **`save(agent, run, tag, progress)`**
  - 先在 checkpoint 目录原子写入 `progress.json`：各阶段累计更新数，以及 corpora、mix、seed。
  - 然后更新 `latest`。
- **新函数 `progress(run)`**：读取 latest 的 `progress.json`，没有则全 0。
- **`build()` 行为不变**：有 latest 就严格恢复完整参数和优化器，忽略 `--init-from`；新 run 才走 `inherit_student`。
- **报告**
  - 写明合约列表、各合约曝光、合并及分合约标签/示范数、全局示范权重。
  - L1 新增 `train_market.json`。
  - `reports()` 收集 market、outcome、policy、value 四类报告。
  - `final_eval` 在 eval 为空时记 None，不再 `eval[-1]` 越界。
- **`freeze(agent, out, name, preset, corpora, teaching, lineage)`**
  - 目标目录已有 `policy.json` 时拒绝写入（π_k 不可变）。
  - 先原子写 `agent.pkl`，再原子写 `policy.json`。
  - 元数据：
    - `policy_id`；
    - `corpora`：每个合约的 contract、fold、funds_floor、gamma、clock、reward_schema、路径；
    - 统一的 `reward_version`；
    - `lineage`：父策略、round、Q 教师策略、CF 列表、κ_Q 口径。
  - 原来单合约的 `corpus` / `teacher` 键去掉，`test_ts_v1_s2.py` 的断言相应更新。
  - CLI 加 `--out`，用来指定快照目录。

## F2：多合约同策略 Q（`thinking_student/value.py`、`run.py`）
- **`QWindows`**：允许 `holdout=0`；拆出 `_pick`。
- **新类 `MultiQWindows(cf_folders, split, holdout, burnin, cf_boost, seed, mix)`**
  - 读每个 `cf/meta.json`。所有 `policy` 的解析路径必须相同，即同一个冻结 π_k，否则列出差异并拒绝。合约重复也拒绝。
  - 每合约一个 `QWindows`，先抽合约再抽窗口，不跨合约。
  - `constant()` 在全部有效行上合并计算。
  - NOT_COMPARABLE 的语义不变：`q_cf_valid=0`，没有 Q 监督，不算作 0 收益。
- **κ_Q 合并估计 `kappa(floor=None)`**
  - 用同轮全部 VALID_COMPLETE 成对样本的 ΔG，按 mix 加权（uniform：每合约总权重相等）算标准差。
  - 同时记录分合约的 std 和对数。
  - 对数 < 2 或 std ≤ 0 时，没配 `kappa_floor` 就报错；配了就用下界并记录 `floored`。std 低于下界时同样处理。
- **`train-value` 与 `freeze --kappa-q auto`** 改用多个 `--cf`。报告和 `value_anchor` 写明 CF 列表、统计口径和对数。
- **RSSM 短窗诊断（C4 §3.1）**
  - 新函数 `window_check(policy, collection, windows, length=64, burnin=16)`，对应 CLI 命令 `state-check`。
  - 做法：对冻结策略，在采集的若干窗口起点把 carry 置零（`is_first=True`），并令 `n_actions = 起点步号`，使策略种子与连续路径对齐；然后用采集记录的决策输入逐步前向，与连续采集时记录的 `delta_q`、`z`、`p_tp_h` 逐行比较。
  - 输出：按窗口内位置分段的平均绝对差、ΔQ 符号一致率、量纲 std。从第 0 步开始的窗口必须完全一致，作为对照。
  - 只做诊断，不设门槛。

## F3：薄编排器（新文件 `thinking_student/formal_train.py`，配置在 `dreamerv3/configs/thinking_student/`）
- **命令：** `pretrain` / `iterate --rounds N` / `evaluate --policy P [--train-smoke]` / `run --rounds N` / `status`。
- **调用方式**
  - 每一步以子进程运行 `python -m dreamerv3.thinking_student.run …` 或 `exam`，复用现有 CLI；每个阶段独占进程，便于释放 GPU。
  - 日志写到 `run_root/logs/`。
  - 并发子进程设 `XLA_PYTHON_CLIENT_PREALLOCATE=false`；同时跑几个合约由配置 `parallel_contracts` 控制。
  - 测试中把 `_call` 换成进程内调用。
- **目录：**
  ```
  run_root/run_state.json  config.yaml  logs/
  foundation/                         # L1→L2→L3 学习 run（init pi0r）
  policies/pi_0000, pi_0001 …         # 不可变快照
  experience/<policy>/collect/<C>/    # π_k 正式采集
  experience/<policy>/cf/<C>/         # Q^{π_k} 教材
  learners/pi_000k/                   # 由 π_{k-1} 继承：L4 + L5 → 冻结 π_k
  eval/<policy>/<DEV|TRAIN_SMOKE>/<C>/
  ```
- **`pretrain`**
  1. 发现合约。
  2. L1、L2、L3 依次执行；剩余更新数 = 配置预算 − `progress`。
  3. 冻结 `pi_0000`，已存在则跳过。
  4. 对两个 TRAIN 合约做短程 TRAIN_SMOKE，确认两边调用的是同一个正式 Student。
- **`iterate`（一轮：π_k → π_{k+1}）**
  1. 选合约：配置名单，或按轮次轮转。
  2. 逐合约 collect：`meta.done` 为真则跳过，否则从 `state.pkl` 续采。
  3. `check`：有违规的合约记 `CHECK_FAILED`，不进入本轮 CF/L4；一个合约都不剩时本轮报错停止。
  4. CF：已有 `meta.json` 且其 policy 为同一 π_k 时跳过；不完整的就单合约整段重跑。
  5. 对首个合约运行 `state-check`。
  6. L4：所有本轮 CF 混合训练。
  7. L5：S4 先验刷新，用全部 TRAIN 教材跑 train-policy；`prior_refresh_updates: 0` 时记 `L5_SKIPPED_BY_CONFIG`。
  8. 冻结 π_{k+1}：β_Q 和合并 κ_Q，写入 lineage。
  9. 评估：配置了 DEV 就跑 DEV，否则跑 TRAIN_SMOKE。
- **`run_state.json`**
  - 原子写入，字段按 C4 §4.3：phase/step/round、contracts、frozen_policy、`latest_candidate`、`best_dev`、各轮的合约及其 collect/CF 状态、`updates_by_stage`、seed、latest_checkpoint。
  - 每轮记录 `L6: L6_NOT_IMPLEMENTED`。
  - 是否完成始终从磁盘产物重新判断，`run_state` 只做镜像，不当作准入依据。
- **配置：** `formal_v1.yaml`（18 合约，预算沿用 C4 示例，标明待用户授权）和 `c4_smoke_2c.yaml`（实跑用）。
  - 用 `yaml.safe_load` 读取，与默认值合并，拒绝未知键。
  - 不新建配置平台。

    - 按 TP/SL/OTHER 分的平仓数，以及期末未完成仓位。

    - 占仓率、权益最大回撤、账户净盈亏、是否跑到真实终点。
    - 学生减随机基线的差值，以及基线各 seed 的分布。
  - **标签：**
    - `DEV`：来自 validation 行；
    - `TRAIN_SMOKE`：来自 TRAIN 教材环境，可截断步数，并标 `complete`；
    - 没配 DEV 时写 `DEV_NOT_CONFIGURED`，不产生成绩。

### 3. 正式训练分段启动：`pretrain --until`

用户要求开发全部完成后，先在 18 个合约上只训练 L1 和 L2。为此新增：
- **`formal_train pretrain --until L1|L2|L3`**：训练到所给阶段为止，不冻结 `pi_0000`。之后再运行 `pretrain`（不带 `--until`），会从已记录的进度接着训练剩余阶段，冻结后进入考试。
- **阶段先后保护：** 某个基础阶段如果后面的阶段已经训练过，或者 `pi_0000` 已冻结，再给这个阶段加预算会被拒绝，而且拒绝发生在任何调用之前。
  - 原因：后面的阶段建立在该阶段的结果上；回头再训，会让 Outcome 头或冻结策略所依据的特征悄悄过期。
  - 需要这样做时，新建一个 run。
- **测试：** `test_orchestrator_rounds_resume_from_the_disk`，覆盖以下几点：
  - `--until L2` 只调用 L1、L2，不冻结；
  - 再次 `pretrain` 只训练 L3，然后冻结；
  - 已冻结后加 L1 预算被拒绝，没有发生任何调用；
  - `--until` 用在 `iterate` 上时报参数错误。

### 4. C4 源码 Review 修复（2026-10-24）

依据 `FG_S3_TS_C4_gy34_d334_Source_Review_20261024.md`。它审查的是 dreamerv3 `69fd0b8`、gym `0056296`，这两个版本的源码与当前 HEAD 相同。逐条核对源码后的结论和做法如下。

- **R1（确认）：冻结后中断会漏掉该候选的考试。**
  - 问题：`iterate` 只看最新冻结的 `pi_k`。达到 `max_rounds` 就返回，没达到就开下一轮，所以 `pi_k` 没做完的考试永远补不上。
  - 修复：每轮开始前先看 `pi_k` 的考试文件。不全就只补缺的部分（`evaluate` 已按合约跳过完成的考试）。
    - k ≥ 1 时，这一步就是把第 k 轮做完，计入本次调用的轮数。所以 `--rounds 1` 的重跑只补考试，不开新轮，与“轮中途中断后重跑只补完该轮”一致。
    - k = 0 时补的是 pretrain 的考试，补完照常开第 1 轮。
  - `exam.json` 改为先写临时文件再改名，它存在就表示考试已完成。
  - 测试：
    - 真实一轮中，冻结后第一次考试失败；重跑只做两次 TRAIN_SMOKE 考试（未配置 DEV）。
    - 两个 DEV 合约中一个已考完；`max_rounds` 为 2、`--rounds 1` 时，重跑只考另一个，不开第 2 轮。
- **R2（确认）：没有有效 CF 成对样本时，Q 锚点照样被启用。**
  - 问题：给了正的 `kappa_floor` 时，0 对有效 CF 也会返回下界，`freeze --beta-q 1` 照常启用锚点。
  - 修复：
    - β_Q > 0 需要 `--cf` 中至少 2 个有效 ADD/WAIT 成对样本。不足时快照保持 β_Q = 0，`value_anchor` 记 `status: Q_ANCHOR_NOT_READY`、请求的 β_Q 和对数，编排器把它记入该轮。
    - `MultiQWindows.kappa` 在少于 2 对时一律报错；下界只替代真实成对样本的零方差或过小尺度。
    - β_Q > 0 却没给 `--cf` 时报错。
  - 测试：
    - 0 对时 `kappa(0.05)` 报错；不少于 2 对且 ΔG 全相同时使用下界。
    - 用 0 对的 CF 冻结，得到 β_Q = 0 和 `Q_ANCHOR_NOT_READY`，rollout 的 anchor 全为 0。
    - β_Q > 0 而没给 `--cf` 时报错。
- **R3（测量，不改训练）：** 用现有 `state-check` 在 1024 行窗口上测量短窗口状态与连续状态的差距，看它随窗口内位置怎样衰减。测两个策略：
  - 从正式 foundation ckpt 22000 冻结的诊断快照（不是 `pi_0000`）；
  - 冒烟的 `pi_0000`，作对照。

  根据结果对 L3 的窗口长度和预热给出建议，由用户决定。
- **R4：** 正式配置的 `state_check_windows` 改为 0，需要诊断时手动运行 `run state-check`。
